# Campus Job Agent 设计说明

- 状态：已通过对话评审
- 日期：2026-07-16
- 项目名：`campus-job-agent`
- 中文名：校园求职 Agent
- 产品形态：本地单用户 Web 应用，面向中国大陆校招与实习

## 1. 背景

用户希望提供自己的简历、经历和求职偏好，让系统从自建公司库及其他公开招聘来源检索岗位，自动过滤和排序适合的机会，随后围绕每个岗位生成定制简历、面试准备内容，并跟踪完整求职进度。系统只提供辅助，最终申请必须由用户检查并手动投递。

本项目面向任何人开源下载。每次安装只服务一个本地用户，不建设在线账号、多租户或云端同步系统。

## 3. 已确认的产品决策

1. 用户检查材料并手动投递，系统永不自动提交申请。
2. 岗位只从公开公司官网、官方 ATS/API 和用户明确导入的数据接入。
3. 第一版是本地 Web 应用，不是命令行工具或在线 SaaS。
4. 项目是通用开源项目，但每个安装实例只管理一个求职者。
5. 第一版聚焦中国大陆校招与实习，不覆盖社会招聘和海外签证场景。
6. 首次使用同时支持上传简历和引导表单；AI 解析结果必须由用户确认。
7. 同时支持 OpenAI 兼容云端 API 和本地 Ollama。
8. 主体技术栈采用 TypeScript 模块化单体：React、Fastify、SQLite、Playwright。

## 4. 产品目标

### 4.1 核心目标

- 建立经过用户确认的候选人事实库和求职偏好。
- 从多个公开来源采集、规范化、去重并验证岗位。
- 先用确定性规则过滤，再用 AI 做可解释匹配。
- 为关注岗位建立独立申请档案。
- 生成可追溯、不可编造事实的定制简历。
- 生成与实际投递简历一致的面试准备材料。
- 用本地看板跟踪投递、笔试、面试、Offer 和淘汰。
- 保护简历、密钥和求职记录，不把隐私写入日志或代码仓库。

### 4.2 非目标

- 自动投递或自动填写招聘表单。
- 代替用户登录招聘网站。
- 绕过验证码、登录限制、访问控制或反爬机制。
- 自动和 HR 聊天或发送消息。
- 云端账户、多人协作、移动端和云同步。
- 第一版同时支持几十个未经验证的数据源。
- 让 AI 自行补全不存在的经历、技能或成果数字。

## 5. 总体架构

系统采用本地模块化单体。生产模式下，由一个 Fastify 进程同时提供本地 API、后台任务和构建后的 React 静态资源。服务只监听 `127.0.0.1`。

```text
React 本地网页
    |
Fastify 本地服务
    |-- profile          候选人档案与事实库
    |-- sources          招聘来源适配器
    |-- jobs             岗位规范化、去重和有效性
    |-- matching         硬过滤与 AI 软匹配
    |-- materials        定制简历与文档导出
    |-- interview        面试准备与复盘
    |-- tracker          申请状态和提醒
    |-- ai-providers     OpenAI 兼容 API 与 Ollama
    |-- tasks            本地任务调度、重试和进度
    `-- storage          SQLite、文件和备份
```

### 5.1 建议仓库结构

```text
campus-job-agent/
  apps/
    web/                 React 前端
    server/              Fastify 本地服务与启动入口
  packages/
    contracts/           跨模块数据模式和 API 类型
    profile/             简历解析与事实库
    sources/             来源接口和内置适配器
    jobs/                规范化、去重和有效性
    matching/            硬过滤与匹配评分
    materials/           简历版本、模板和导出
    interview/           面试准备和 STAR 故事
    tracker/             状态机、提醒和统计
    ai-providers/        模型提供商抽象
    storage/             数据库、迁移、文件和备份
    testing/             跨包测试夹具和虚构黄金样本
  prompts/               可审阅、可版本化的 AI 规则
  templates/             简历和面试材料模板
  docs/                  用户、开发和安全文档
```

每个包只暴露公共接口，不能跨包直接访问其他包的私有数据库表或实现文件。

## 6. 系统数据与用户数据边界

### 6.1 系统层

系统层包括源代码、提示词、数据模式、数据库迁移、内置适配器、文档模板、测试和文档，可通过 Git 或发行包更新。

### 6.2 用户层

用户层位于操作系统的应用数据目录，不存放在项目仓库中，包括：

- SQLite 数据库
- 原始简历和附件
- 原始 JD 和公开页面快照
- 定制简历 PDF、DOCX 和中间结构化数据
- 面试准备与复盘文件
- 扫描缓存和任务记录
- 用户配置和备份

更新系统层不得覆盖用户层。数据库升级必须在备份后通过带版本号的迁移执行。

## 7. 核心数据模型

### 7.1 候选人事实

每条事实包含：

- 唯一 ID
- 类型：教育、实习、项目、技能、证书、课程、成果或 STAR 故事
- 结构化内容
- 来源：原始简历、用户手动填写或用户确认的 AI 解析
- 验证状态
- 创建与更新时间
- 可选的证据附件引用

只有用户确认的事实可以进入正式匹配报告、定制简历和面试回答。

### 7.2 求职偏好

至少包含：

- 毕业时间和招聘届别
- 校招、日常实习或暑期实习偏好
- 目标岗位方向和排除方向
- 可接受城市和远程偏好
- 期望薪资或薪资底线
- 学历、专业和语言信息
- 可实习起止时间、每周到岗天数和实习时长
- 行业与公司偏好
- 公司黑名单

### 7.3 岗位

统一岗位模型至少包含：

- 公司、岗位名称和岗位类别
- 校招或实习、招聘届别和批次
- 城市和远程属性
- 学历、专业和语言要求
- 职责、技能和资格要求
- 实习时长、每周到岗天数和转正机会
- 发布时间和截止时间
- 原始链接、来源、采集时间和原始 JD
- 解析置信度和岗位有效状态
- 规范化指纹

### 7.4 申请档案

每个关注岗位创建一个独立申请档案，包含：

- 锁定的岗位快照
- 匹配报告
- 定制简历版本
- 用户实际投递的简历版本
- 面试准备包和复盘
- 当前状态、状态事件和提醒
- 用户笔记、淘汰原因和最终结果

## 8. 用户首次使用流程

1. 用户选择上传 PDF/DOCX 简历或从空白表单开始。
2. 系统解析教育、实习、项目、技能和成果。
3. 所有 AI 提取内容以待确认状态展示。
4. 用户逐项确认、修正或删除。
5. 引导表单补齐届别、目标岗位、城市、实习可用时间和偏好。
6. 用户选择 OpenAI 兼容 API 或 Ollama，并执行连接测试。
7. 系统生成本地事实库，进入岗位发现页面。

解析失败时必须保留原文件并允许手动填写，不能阻塞整个应用。

## 9. 岗位来源适配器

### 9.1 适配器职责

每个适配器只负责：

- 声明来源名称、能力和访问规则
- 发现岗位列表
- 获取公开岗位详情
- 输出原始来源记录
- 给出抓取时间、来源 URL 和错误类型

适配器不负责候选人匹配、跨来源去重、申请状态或 AI 生成。

### 9.2 访问规则

- 公开 API、RSS 或结构化数据优先。
- 静态 HTML 使用轻量解析器。
- 只有动态渲染确有必要时才使用 Playwright。
- 必须设置超时、并发限制、来源级限速和缓存。
- 不访问需要登录的内容，不绕过验证码和访问控制。
- 定时扫描仅在本地应用运行时执行。

### 9.3 第一批来源

- 自建芯片公司库及经过验证的官方招聘入口。
- 岗位 URL/JD 粘贴。
- CSV/JSON 批量导入。
- 腾讯招聘公开 JSON API 适配器，作为第一版可靠自动来源；该接口已于 2026-07-16 验证可以无需登录返回结构化岗位列表和完整 JD。
- 企业招聘官网与公开 ATS/API 的扩展接口。

来源适配器失败时，不得用猜测数据填充，也不能将此前岗位批量误标为过期。

## 10. 岗位处理流水线

```text
公开来源
  -> 保存原始快照
  -> 解析
  -> 模式校验
  -> 统一格式
  -> 指纹和 URL 去重
  -> 有效性检查
  -> 硬条件过滤
  -> AI 软匹配
  -> 推荐候选池
```

### 10.1 去重

去重综合使用规范化 URL、公司名、岗位名、城市、招聘批次和 JD 内容指纹。跨网站重复岗位合并为一条规范记录，同时保留全部来源链接。

### 10.2 有效性

岗位可处于未知、有效、疑似过期、已过期或来源不可访问状态。一次访问失败不能直接判定过期；只有明确截止时间、页面明确关闭或连续多次验证失败并满足规则时才更新状态。

## 11. 匹配设计

### 11.1 硬条件过滤

硬条件由确定性代码执行，不调用 AI：

- 招聘届别
- 学历资格
- 城市可接受性
- 实习时间、时长和到岗天数
- 用户明确不具备且岗位强制要求的资格
- 岗位有效性
- 公司黑名单

被过滤岗位进入可查看的“已过滤”列表，显示原因，并允许用户手动恢复。

### 11.2 AI 软匹配

软匹配总分 100：

- 求职方向匹配：25
- 技能和关键词匹配：25
- 实习、项目和课程证据：20
- 岗位职责可迁移能力：15
- 公司与行业偏好：10
- 成长价值：5

匹配输出必须包含总分、各维度分数、推荐等级、事实证据、明确缺口、投递理由、简历强调建议和置信度。

只有通过硬条件的新增或已变化岗位调用 AI。输入未变化时使用缓存，避免重复费用。AI 无法确认的信息不得作为硬性淘汰依据。

“自动锁定”表示自动进入推荐候选池并排序。只有用户选择“关注”或“准备投递”后才创建申请档案。

## 12. AI 提供商抽象

统一接口至少覆盖：

- 连接测试
- 结构化生成
- 流式文本生成
- 模型能力和上下文限制
- 超时、取消、重试和用量信息

内置实现：

- OpenAI 兼容接口，可配置 Base URL、模型名和 API 密钥，以支持 OpenAI、DeepSeek、通义千问等兼容服务。
- Ollama 本地接口。

所有结构化输出必须通过运行时数据模式校验。网页或 JD 中的提示注入文本只能作为不可信数据，不能覆盖系统规则、访问本地文件或触发工具调用。

## 13. 定制简历

### 13.1 生成规则

- 原始简历只读，定制简历始终是新版本。
- AI 可以重排、压缩、改写和强调，但不能生成新事实。
- 每个关键条目关联事实 ID。
- 不具备的要求作为缺口展示，不通过关键词堆砌隐藏。
- 用户可以逐项接受、修改或拒绝改写。

### 13.2 流程

```text
关注岗位
  -> 创建申请档案
  -> 读取岗位快照、匹配报告和事实库
  -> 选择相关事实
  -> 生成结构化简历草稿
  -> 事实引用和冲突校验
  -> 原版与定制版差异
  -> 用户确认
  -> PDF/DOCX 导出
```

结构化简历是唯一编辑源，同一份数据生成网页预览、PDF 和 DOCX，防止格式之间内容漂移。

### 13.3 导出校验

- 联系方式完整
- 教育、日期和经历一致
- 关键词覆盖合理
- PDF 文本可正常提取
- 无乱码和异常阅读顺序
- 页数符合用户设置
- 文件名包含公司和岗位
- 定制版与事实库无冲突

## 14. 面试准备

当申请进入笔试或面试状态，系统基于锁定的岗位、实际投递简历和已有复盘生成：

- 公司和岗位摘要
- 岗位要求逐项拆解
- 专业问题、简历深挖和行为问题
- 基于真实事实的 STAR 回答提纲
- 对技能缺口的诚实桥接回答
- 自我介绍和求职动机
- 可向面试官提出的问题
- 实际投递简历中最可能被追问的内容

每轮保存日期、面试官信息、真实问题、用户复盘和结果。后续轮次优先使用前一轮反馈。任何答案都不得与实际投递简历冲突。

## 15. 求职进度

默认状态：

```text
已发现 -> 已关注 -> 准备投递 -> 已投递 -> 笔试 -> 一面
        -> 二面/后续面试 -> Offer
        -> 已拒绝 / 已放弃 / 已过期
```

状态由用户手动更新。系统维护当前状态和不可变的状态事件历史，并提供截止日期、面试日期、待办、状态看板、筛选、投递统计、转化率和淘汰原因分析。

## 16. 本地存储与备份

SQLite 是结构化数据的主存储。原始文件、网页快照和生成文档存放在用户数据目录。数据库写入使用事务；文件先写临时文件，校验成功后原子替换。

备份包包含数据库、用户文件和数据模式版本，默认不包含 AI 密钥。恢复过程必须验证版本和文件完整性。

## 17. 隐私与安全

- 服务只监听 `127.0.0.1`。
- API 密钥不进入 SQLite、日志、备份或 Git。
- 密钥优先使用操作系统凭据管理器，也允许通过环境变量提供。
- 调用云端模型前明确显示将发送的数据范围。
- 匹配默认移除姓名、电话、邮箱和身份证明等无关信息。
- Ollama 模式下简历和 JD 不离开本机。
- 用户可以删除单个档案或清除全部个人数据。
- 上传文件必须经过大小、类型、路径和内容安全检查。
- 本地 API 必须验证来源，防止其他网页调用本地服务。

## 18. 错误处理

### 18.1 来源失败

- 保留上次成功结果。
- 隔离单一来源故障。
- 显示结构变化、超时、访问受限等明确错误。
- 不因一次失败把旧岗位标记为过期。

### 18.2 解析置信度低

- 进入待确认列表。
- 同时展示原始内容和解析结果。
- 用户确认前不参与自动匹配。

### 18.3 AI 失败

- 短暂错误最多自动重试两次并采用退避。
- 输出必须通过模式和事实校验。
- 无法修复时保留现有草稿，不写入正式报告。
- 支持切换模型后重新生成。

### 18.4 文档失败

- 保留结构化简历和网页预览。
- 明确指出 PDF、DOCX 或字体失败环节。
- 不丢失用户确认过的内容。

### 18.5 迁移失败

- 升级前自动备份。
- 迁移在事务中执行。
- 失败后回滚并停止启动，避免半升级状态。

## 19. 测试策略

### 19.1 单元测试

- 岗位模式和规范化
- 届别、学历、城市和实习可用性过滤
- URL 与 JD 指纹去重
- 匹配维度计算
- 状态机和状态事件
- 事实引用与冲突校验
- 文件名、上传和路径安全

### 19.2 适配器测试

- CI 使用保存的公开页面样本，不依赖真实网站。
- 每个适配器必须覆盖成功、空列表、页面变化、超时和限流。
- 提供独立、可选的在线健康检查。
- 页面结构变化必须显式失败，不能悄悄返回空数据。

## 21. 第一版验收条件

第一版只有同时满足以下条件才算可用：

1. 新用户能在 Windows 上按文档启动。
2. 能上传中文简历并人工确认事实库。
3. 能配置至少一种 OpenAI 兼容模型和 Ollama。
4. 能通过腾讯招聘公开 JSON API 和已验证官方招聘源自动发现岗位，并支持手动导入。
5. 能正确去重、过滤并给出带证据的匹配报告。
6. 能关注岗位并在看板中更新状态。
7. 能生成不包含虚构事实的定制简历并导出。
8. 能基于实际投递简历生成面试准备包。
9. 适配器或模型失败不会损坏已有用户数据。
10. 测试不会使用真实用户简历、真实密钥或真实申请记录。

## 22. 主要风险与缓解措施

- 官方招聘页面可能暂时不可用：按来源隔离、退避，并以手动导入和其他公开来源降级。
- 招聘页面频繁变化：来源隔离、固定样本、变化检测和显式错误。
- AI 虚构事实：确认状态、事实 ID 引用、冲突检查和用户批准门。
- 模型成本过高：硬过滤优先、缓存、批次限制和可见用量。
- 本地安装复杂：单一 TypeScript 运行时、自动环境检查和分阶段打包。
- 文档格式不一致：结构化简历作为唯一编辑源。
- 本地数据丢失：原子写入、迁移前备份和可验证的备份恢复。
